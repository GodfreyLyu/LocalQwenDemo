# Local platform: krunkit + Terraform

This directory configures a single-node `krunkit/containerd` cluster that has already
been started with the Minikube CLI. The only Terraform root module is
`terraform/platform`. It manages custom namespaces and the generic-device-plugin, with
optional Argo CD and monitoring installations enabled by `argocd_enabled = true` and
`monitoring_enabled = true`. Both Helm releases are disabled by default. Terraform does
not use a Minikube provider or `local-exec`, and does not start the cluster. See the [GitOps
guide](../../docs/guides/gitops.md) for setup and the order of the first sync.

## Files and state

- `scripts/start-minikube.sh`: starts a new cluster or resumes an existing one. It
  leaves running profiles as configured.
- `scripts/verify-gpu.sh`: checks nodes, the DaemonSet and `devic.es/dri` registration
  without changing resources.
- `terraform/platform/terraform.tfvars.example`: example settings that can be committed.
- `terraform/platform/terraform.tfvars`: local settings, excluded by `.gitignore`.
- `terraform/platform/.terraform.lock.hcl`: the provider lockfile generated by
  Terraform; commit this file.
- `kubernetes/tests/gpu-smoke-test.yaml`: a manually managed test Pod, outside Terraform
  state.

Terraform stores state locally. Git ignores `.terraform/`, `*.tfstate*` and `*.tfplan`.
Keep the state so Terraform can correctly update or remove these platform resources
later. Do not manage the same resources from another root module.

## Initialize and review the plan

Run from the repository root. Skip the startup script if the cluster is already running.
For a new profile, the script defaults to 4 CPUs and 8192 MiB of memory. Set
`MINIKUBE_CPUS` and `MINIKUBE_MEMORY` before starting it to choose a different size;
these variables do not resize an existing profile. Install the krunkit driver before
using this script; the device plugin is installed by Terraform in the following steps.

```bash
infra/local-platform/scripts/start-minikube.sh --profile minikube
```

```bash
terraform -chdir=infra/local-platform/terraform/platform init
```

```bash
terraform -chdir=infra/local-platform/terraform/platform validate
```

```bash
terraform -chdir=infra/local-platform/terraform/platform plan
```

The defaults and `terraform.tfvars.example` use the `minikube` context. Copy the example
to your local `terraform.tfvars` and adjust it before the first run. Both providers
explicitly use the same kubeconfig and context. They do not rely on `kubectl config
current-context` or automatically read `KUBECONFIG`. The scripts use `KUBE_CONFIG_PATH`
to select one kubeconfig file, defaulting to `$HOME/.kube/config`. If you change this
path, also set Terraform's `kubeconfig_path`.

The default plan should create four namespaces (`gpu-system`, `gpu-tests`, `argocd` and
`monitoring`) and one DaemonSet. If resources with those names already exist, check
their ownership before importing them or choosing different names. Do not run another
device plugin that registers the same `devic.es/dri` resource in a different namespace
at the same time.

After reviewing the plan, apply it and verify the deployment:

```bash
terraform -chdir=infra/local-platform/terraform/platform apply
```

```bash
infra/local-platform/scripts/verify-gpu.sh --profile minikube
```

## GPU resources and testing

The plugin explicitly sets `--domain=devic.es` and exposes only `/dev/dri/renderD128` as
`devic.es/dri`. Its image is pinned to the multi-architecture digest for
generic-device-plugin 0.2.0, which includes ARM64.

The plugin needs privileged access and the kubelet socket. The test Pod uses neither
privileged mode nor hostPath. It requests the extended resource to access the device,
then checks and opens the render node as UID 1000.

The default `gpu_slots = 1` allows only one Pod to request the device at a time.
Increasing this value lets Pods share the same GPU; it adds no physical GPUs or GPU
memory isolation. After changing it, verify with `--expected-slots N`. A node's
`allocatable` value is its total schedulable capacity and does not decrease as Pods use
the resource.

Run the smoke test before starting Ollama, or while the GPU slot is free. With the
default single slot, the test cannot schedule while Ollama holds it.

```bash
kubectl --context minikube apply -f infra/local-platform/kubernetes/tests/gpu-smoke-test.yaml
```

```bash
kubectl --context minikube -n gpu-tests wait --for=jsonpath='{.status.phase}'=Succeeded pod/gpu-smoke-test --timeout=150s
```

```bash
kubectl --context minikube -n gpu-tests logs gpu-smoke-test
```

```bash
kubectl --context minikube -n gpu-tests delete pod gpu-smoke-test
```

Before repeating the test, delete the previous test Pod. If you change the default
namespace, update the test YAML as well. If your kubeconfig is stored elsewhere, add
`--kubeconfig` to the kubectl commands above. The test needs read and write access to
the node's render device as UID 1000. Check the device permissions on your node if
the access check fails.

This test verifies scheduling, device injection and successful device access. It does
not test Vulkan, model inference or GPU utilization. Inference workloads also need
userspace drivers and an inference image that support the krunkit virtio GPU. The
repository's `scripts/minikube_demo.sh` requires the Docker driver and cannot be
used for this krunkit platform.

If the test fails, inspect the logs and resources:

```bash
kubectl --context minikube -n gpu-system logs daemonset/generic-device-plugin
```

```bash
kubectl --context minikube -n gpu-tests describe pod gpu-smoke-test
```

```bash
kubectl --context minikube describe node minikube
```

`terraform destroy` deletes the namespaces managed here and everything in them,
including resources added manually later. It does not delete the Minikube VM. Although
the test Pod is outside Terraform state, deleting the `gpu-tests` namespace also deletes
that Pod.

## Monitoring

Terraform owns the `monitoring` release of kube-prometheus-stack, pinned to Chart
92.10.1 (Prometheus Operator v0.94.1). The Chart requires Kubernetes 1.25 or later and
its configured images support Linux ARM64. It installs Prometheus, Grafana,
Alertmanager, kube-state-metrics and node exporter. The application Chart owns its
ServiceMonitor, PrometheusRule and dashboard ConfigMap in `local-review-demo`; keep
those resources out of Terraform state.

First apply the platform with monitoring disabled to create its namespace. Prepare
`local-review-demo` through the existing application bootstrap and create the Grafana
admin Secret once. Use private local files, not Terraform variables or Helm values,
for credentials. The files below must contain the chosen admin username and password;
they are not committed or printed by the platform:

```bash
kubectl --context minikube -n monitoring create secret generic monitoring-grafana-admin --from-file=admin-user=/path/to/grafana-admin-user --from-file=admin-password=/path/to/grafana-admin-password
```

Keep this Secret stable across upgrades. Its two keys are `admin-user` and
`admin-password`; the Terraform configuration references only its name. The Grafana
sidecars can read ConfigMaps in `monitoring` and `local-review-demo`, without Secret
read access. This requires the application namespace to exist before enabling the
release, because Helm creates a Role and RoleBinding there.

Set `monitoring_enabled = true` in the ignored `terraform.tfvars`, review the plan,
and apply. Wait for the operator and CRDs before enabling the application's monitoring
values in its normal release workflow. Prometheus selects resources labelled
`release: monitoring` from `monitoring` and `local-review-demo`. Grafana loads
dashboard ConfigMaps labelled `grafana_dashboard: "1"` from those same namespaces.
Application changes do not replace this platform release or restart Ollama.

The configured budget uses a 30-second scrape/evaluation interval, one-day retention,
a 4 GiB TSDB retention cap and a 5 Gi PVC on `standard`. Time and size limits both
apply; the earlier limit wins. WAL and head-block space still need free disk, and
hostpath PVC size is not a reservation or backup. Running monitoring containers request
345m CPU and 1288 MiB memory in total, with memory limits of 3360 MiB; check node
allocatable minus existing requests as well as actual usage before installation.
Grafana requests 384 MiB and has a 768 MiB limit to leave room for dashboard queries
and plugins.
Free node disk must also cover image downloads, TSDB data, WAL and kubelet eviction
headroom. A successful Terraform plan or PVC bind does not establish capacity.
Grafana dashboards and data sources are provisioned from Git. Grafana UI changes
and Alertmanager silences are not retained after Pod replacement. Alertmanager
displays alerts locally; no external receiver is configured.

API server, kubelet/cAdvisor, workload, node and storage monitoring remain enabled.
The Minikube profile disables scraping and associated rules for unexposed etcd,
controller-manager, scheduler and kube-proxy endpoints. Node exporter observes the
Linux VM, not macOS host pressure. Container metrics for `review-ollama` describe
model-server resources; backend container metrics do not. GPU device allocation is
not a GPU utilization measurement.

The node-exporter Pod includes a small BusyBox sidecar that measures allocated
bytes with `du -sk` every 30 seconds for Minikube hostPath PVCs in
`local-review-demo` and `local-inference`. Only those provisioner directories are
mounted read-only; the collector has no Kubernetes API token and only the
`DAC_READ_SEARCH` capability to traverse workload-owned directories. Textfile
metrics use a separate writable memory volume. The dashboard prefers kubelet
volume statistics when available and omits fallback samples older than 120 seconds.
PVC requests are displayed separately and are not enforced hostPath quotas.

All monitoring UIs remain ClusterIP services. Use separate terminals as needed:

```bash
kubectl --context minikube -n monitoring port-forward service/monitoring-grafana 3000:80
```

```bash
kubectl --context minikube -n monitoring port-forward service/monitoring-kube-prometheus-prometheus 9090:9090
```

```bash
kubectl --context minikube -n monitoring port-forward service/monitoring-kube-prometheus-alertmanager 9093:9093
```

Use the [observability runbook](../../docs/operations/observability.md) to verify targets,
rules and application metrics. A healthy Helm release alone does not establish that
the application target is scraped or that inference completed successfully.

For an upgrade, review the pinned Chart's release notes and CRD changes first. Helm
installs CRDs on the first installation but does not automatically upgrade or delete
them; this configuration leaves the upstream experimental CRD upgrade job disabled.
Apply any required CRD update from the reviewed Chart before updating the release.
Disabling monitoring removes the Helm release. Prometheus PVCs created by its
StatefulSet and CRDs require separate inspection before cleanup; destroying the
Terraform-managed `monitoring` namespace removes all data and Secrets in it.
